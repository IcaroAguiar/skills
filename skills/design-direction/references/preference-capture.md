# Preference Capture

Treat a screenshot, reference, or comment as evidence of a candidate preference, not automatic authorization to change the design direction.

## Sequence

1. Describe the observed signal.
2. Identify the problem it prevents or the outcome it seeks.
3. Formulate a rule independent of the specific solution.
4. Classify it as principle, heuristic, preferred pattern, anti-pattern, or exception.
5. Define applicable and non-applicable contexts.
6. Define verifiable criteria.
7. Check existing rules for conflict, duplication, or a narrower authoritative home.
8. Propose the smallest exact change.
9. Wait for explicit approval.
10. Incorporate only the approved change into its single source of truth.

## Candidate output

```text
Identified preference:
Evidence:
Problem or intent:
Proposed rule:
Classification:
Applicable contexts:
Non-applicable contexts:
Exceptions:
Verifiable criteria:
Conflicts or duplication:
Exact proposed change:
Status: awaiting approval
```

## Promotion filter

Answer:

1. What use problem does the rule solve?
2. Does it affect clarity, efficiency, accessibility, error, or task completion?
3. Does it generalize beyond one product?
4. Where is the criticized pattern legitimate?
5. Can the rule be verified?

If the rationale is only visual preference, retain it as aesthetic preference. Promote it to a design heuristic only when it has a demonstrated effect on comprehension, effort, error, or completion.

A strong rule states intent, gives a positive target, defines exceptions, remains technology-independent, and can be audited. Replace vague requests such as “more premium,” “modern,” or “clean” with observable criteria.

**Complete when:** the candidate has a single authoritative destination and explicit approval status.
