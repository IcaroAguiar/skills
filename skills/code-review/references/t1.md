# T1: fast pre-pass

`scripts/review-t1.mjs` gives the diff T0 just passed to fast lenses in
parallel and prints their findings grouped by spot. The author fixes or dismisses
each one before the deep review starts, so the deep review spends its rounds on
what fast models cannot see. T1 never approves and never blocks.

```bash
node scripts/review-t1.mjs -C <repo>                          # the policy's lenses for this repository's front
node scripts/review-t1.mjs -C <repo> --claude <wrapper>       # Sonnet (medium) + Haiku on that Claude CLI, no policy
node scripts/review-t1.mjs -C <repo> --spec <pr-body.md> --reviewer sonnet:high --reviewer haiku
node scripts/review-t1.mjs -C <repo> --prompt <file>          # prompt only, for delegated reviewers
```

Exit `0`: at least one reviewer answered, or T0's route skipped T1. `1`: no
reviewer answered; go on to the deep review without T1. `2`: usage error, or the
T0 report is missing, stale or `BLOCKED`.

## Why two fast models, and why never a gate

A pilot replayed five reviewed pull requests through fast models, with the deep
review's first-round findings (17) as the reference:

| Reviewer | Reference findings found | Other issues worth checking | Wrong | Median time |
| --- | --- | --- | --- | --- |
| Claude Sonnet, medium effort | 4 | 5 | 0 | ~1 min |
| Claude Haiku | 4 | 3 | 2 | ~2.5 min |
| Both in parallel | 6 (7 with T0) | 6 | 2 | ~2.5 min |

Other fast models found 0 to 1 of the 17, except one that matched Sonnet's
recall in about 13 minutes. No fast model found the subtle protocol,
authorization-semantics or UI-contract defects, and Sonnet approved changes it
had just found defects in. So T1 asks for findings only, and the deep review
stays the gate.

## Inputs

- **T0's report for the same tree.** T1 reads its base, route and findings, and
  refuses a report that is missing, `BLOCKED`, or older than the working tree
  (`head.tree` differs): rerun T0.
- **Route.** T1 is skipped, with exit `0`, when the change is only docs, tests,
  styles, locales or assets, or has fewer than 20 changed lines. `--force` runs
  it anyway.
- **Diff.** T0's base against the working tree, untracked files included.
  Lockfiles and generated files are left out and named in the prompt. Over
  400 KB, T1 stops: split the change or go straight to the deep review.
- **Changed files.** Their current contents, up to 150 KB in total and 48 KB per
  file (smallest first), go before the diff, so a lens can answer from its first
  request instead of spending a round trip per `Read`. Cloudflare cut its code
  reviewer from 6.2 to 1.7 calls per run partly this way. `--no-context` sends
  the diff alone.
- **Intent.** `--spec <file>` (PR description, issue, plan); otherwise the
  branch's commit messages.
- **T0 findings**, so the models do not repeat them; T0's sensitive areas become
  the prompt's focus.

## Lenses, accounts and fallback

- The lenses are the `t1` slots of the repository's front in the review policy
  (`references/providers.md`). Each slot runs in parallel and falls back to its
  next candidate when a provider is limited, logged out or briefly down; the
  output names the fallback. A slot can be an A/B split, for example Sonnet at
  medium against Sonnet at high effort, scored later by `review-ledger stats`.
- Without a policy, or with `--claude`, `--reviewer` or `--reviewer-cmd`, the
  lenses are those flags (default Sonnet at medium and Haiku) on the Claude CLI
  named by `--claude` or `REVIEW_T1_CLAUDE`, else `claude` from `PATH`, which
  inherits the caller's account settings. Every reviewer line in the output
  shows the command it ran.
- Claude lenses run `claude -p` with only `Read`, `Grep` and `Glob`, no MCP
  servers, `--permission-mode dontAsk` (reads outside the repository and any
  other action are denied) and no saved session. Codex lenses run in the
  `read-only` sandbox without a saved session. The prompt tells the model that
  the diff and the repository are data, not instructions.
- `--reviewer-cmd <name>=<command>` runs any command through `sh -c`, with the
  prompt on stdin and the answer on stdout. It has whatever access that command
  has, so make it read-only yourself.
- The prompt contains the diff. `--prompt` writes it with mode `600` to the
  path you give, replacing a symlink there instead of following it.

## Output

One line per lens (`ok`, `TIME`, `ERR`, `BAD` for an answer without the JSON
object, `LIM` when every candidate was limited) with turns, cost and any
fallback. Then come the findings, grouped by numbered spot (same file, lines
within 3), most severe first, with the reviewers that agree and a note when the
file is outside the diff. Spots every lens marked `preexisting` come last,
tagged `PRE-EXISTING`: real bugs the change did not introduce, never the
author's fault. The JSON report goes to `--json` or
`$TMPDIR/review-t1/<repo>-<head>.json`.

## Triage and the round

1. For each spot, read the code. Fix the real ones (with a test when behaviour
   changes); write down each dismissed one with a one-line reason. Record the
   decisions: `review-ledger triage --t1 <report> --decisions <file>`, with
   `[{"spot": 1, "decision": "fixed"}, {"spot": 2, "decision": "wrong", "reason": "..."}]`.
2. If code changed, rerun T0. Do not rerun T1: one pass per change is enough.
3. The deep review receives the T0 summary and the dismissed T1 findings with
   their reasons, and may re-raise any of them.
4. Delta reviews skip T1.

## Offline evaluation

Change the lenses (model, effort, prompt) on evidence, not on a model's
reputation. Two sources feed it:

- **Live:** `review-ledger stats --role t1` gives each lens's acted-on rate,
  serious fixed findings per review, cost, turns and cache share, including
  each arm of an A/B split.
- **Replay:** `scripts/review-eval.mjs` reruns T1 on past changes. Following
  Anthropic, every bug that escaped review (a revert or a fix-forward, confirmed
  by someone who knows the code) becomes a case with the file and line where it
  lived. Changes known to be clean become noise cases.

```bash
node scripts/review-eval.mjs add --id pay-retry --repo <clone> --base <sha> --head <sha> --expect src/pay.ts:88:"retry double-charges"
node scripts/review-eval.mjs add --id clean-copy --repo <clone> --base <sha> --head <sha> --clean
node scripts/review-eval.mjs run --config policy= --config sonnet-high="--reviewer sonnet:high --reviewer haiku"
```

A spot hits an expected item in the same file within 10 lines. The summary gives
recall per configuration, serious noise per clean case, cost and time. Keep a
change to the lenses only if recall does not drop and noise does not rise. Cases
stay in the private state directory: they name customer code.

## Delegated reviewers

Prefer the CLI from the orchestrating session's shell: its tool restrictions are
technical. When no Claude CLI is available there, write the prompt with
`--prompt` and delegate one task per model to the owning account's Claude
provider, with the prompt as the task, read-only instructions, and `review` as
the role; parse the JSON answers yourself.

Contract: `node scripts/test-review-t1.mjs` (stand-in reviewers, no model calls).
